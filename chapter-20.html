第 19 章：CubeSandbox——从集群入口走到 microVM

先把产品宣传还原成组件

CubeSandbox 的中文 README 将它定位为基于 RustVMM 与 KVM 的沙箱服务，提供单机与集群部署及 E2B SDK 兼容入口。[13] 这里 RustVMM 是构建虚拟机监视器的组件生态，KVM 是 Linux 虚拟化能力；不能据此把 CubeSandbox 直接称为 Firecracker 的包装。

仓库还包含来自 Cloud Hypervisor 路线的 hypervisor 代码与文档。阅读这类工程时，应查实际运行的组件和构建配置，而不是仅凭“Rust 写的 microVM”认定两个产品使用同一个 VMM。

一条主线看懂名字

SDK → CubeAPI → CubeMaster → Cubelet → CubeShim → VMM → microVM

CubeAPI 提供外部 REST 接入；CubeMaster 负责集群层调度；Cubelet 负责节点上的生命周期；CubeShim 在运行时接口与 microVM 管理之间搭桥。其余组件围绕这条主线提供网络、存储和运维能力。

CubeProxy 负责访问沙箱里暴露的服务，CubeEgress 负责外部访问策略和相关代理能力，CubeCoW 负责写时复制卷与快照。可以用“进门、出门、保存房间状态”记忆它们，但仍需看部署中是否启用并配置了这些组件。

从两份源码找证据

CubeAPI/src/routes.rs 列出了沙箱、模板、快照等接口，并给普通请求与暂停恢复、快照长操作分配不同的路由超时预算。这能帮助理解：请求等待预算与沙箱整体生命周期不是同一个参数。

CubeAPI/src/services/sandboxes.rs 能看到服务调用 CubeMasterClient、转换网络与生命周期配置，并限制部分可注入的环境变量名。这是 API 参数向内部执行意图转换的一环。仅看到校验列表，不能证明所有可能绕过方式都已排除；本次没有进行攻击测试。

文档也需要交叉核对

本次快照中，产品架构页有“Redis 是唯一可信源”的表述，而较具体的 Kubernetes 架构表列出 CubeAPI 读写 MySQL、Redis 承担 Proxy 与 lifecycle 状态等分工。它们至少需要结合部署形态和版本解释，不能合并成一条毫无条件的数据库结论。

这给学习者一个真实例子：发现文档差异时，记下路径、提交与冲突点，继续检查配置和实现。不要因为是官方资料就忽略差异，也不要凭这一处差异认定整个项目不可用。

如何理解快照与自动唤醒

它们适合多轮编码和长期工作空间：环境空闲时节省活跃资源，下次访问再恢复。但保存状态会产生存储、版本兼容和恢复时延问题。网络连接、外部令牌和已经发生的远程副作用，不会因为恢复内存就自动回到过去。

初学者先沿中文快速开始跑通虚构数据，再查安全代理配置、快照语义和清理行为。涉及宿主机内核、KVM 或节点初始化的部署步骤，应在专用测试环境按官方条件进行。
